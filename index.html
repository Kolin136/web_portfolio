PDF 기반 RAG 챗봇 구축
(청킹·검색 전략 점진적 고도화)

2026.05 ~ 2026.07 · github.com/Kolin136/Chatbot

[소개]

PDF 문서를 업로드하면 문서의 구조적 특성에 맞는 (청킹 → 벡터DB 저장 → 검색) 전략 조합을 적용해 답변하는 100% 로컬 RAG 파이프라인

[주 기술 스택]

  • LM Studio
  • ChromaDB
  • FastAPI
  • Docling
  • LangChain
  • pydantic_ai

[도입 배경]

  • 범용 LLM의 특정 도메인 지식 부족 문제와, 외부 API 호출 비용 상황 → LM Studio 기반 로컬 추론으로 문서가 외부로 전송되지 않는 구조를 자력 구축
  • 단일 전략(고정 크기 청킹 + 임베딩 검색)으로는 문서 종류에 따라 검색 정확도 편차가 크다는 점을 확인, 문서 형태별로 전략을 조합·선택할 수 있는 구조를 목표로 설계

[기능 흐름]

  1. PDF 업로드 → Docling 파싱 (텍스트 / 표 / 이미지 분리)
  2. 표·이미지는 멀티모달 LLM으로 텍스트 설명문 변환 후 본문 청크에 결합
  3. 문서 시각 구조 분석 → 청킹 전략 선택 (구조형 → Hybrid / 서술형 → Semantic)
  4. 청크 결과 임베딩 후 ChromaDB 저장
  5. 질의 시 하이브리드(Dense + Sparse) 검색 → RRF 순위 융합 → 원본 텍스트로 답변 생성

1청킹, 임베딩 시 문서 내 시각 요소(표·이미지) 유실 문제 해결

[문제 상황]

  • 문서의 표와 이미지가 포함된 경우 청킹 단계에서 통째로 누락 후 임베딩 대상에서 제외되는 문제 발생

[해결 과정]

  • Docling으로 PDF를 파싱해 텍스트, 표, 이미지 등을 구조적으로 분리하고, 시각 요소를 별도 객체로 추출
  • 추출한 시각 요소를 멀티모달 LLM을 통해 텍스트 설명문으로 변환한 뒤, 해당 요소가 위치한 본문 청크에 결합하여 하나의 검색 단위로 인덱싱

[성과]

  • 표·다이어그램에만 존재했던 정보가 텍스트 검색 경로로 편입되어, 기존에는 근거 부재로 답변 불가 발생
  • 표·이미지에 근거가 있는 질의 기준 RAGAS(RAG 평가 시스템) 4개 지표 전부 향상

2청킹 전략 고도화: 고정 크기 → 구조 기반 → 의미 기반

[문제 상황]

  • 고정 크기 청킹은 토큰 수만 기준으로 자르기 때문에 문단·문장 중간에서 문맥이 단절되고, 질문과 관련된 내용이 두 청크에 걸쳐 쪼개져 검색 정확도가 떨어지는 현상 발생

[1차 적용: Docling HybridChunker]

  • Docling이 제공하는 HybridChunker를 적용해, 헤딩·단락 구조를 그대로 보존한 채 임베딩 모델의 토크나이저 기준 최대 토큰 수에 맞춰 청크를 병합·분할하도록 구성
  • 청크 경계를 문서에 이미 존재하는 헤딩·문단 구분선에 맞춰, 문단 중간이 아닌 구조적 경계 지점에서만 청크가 나뉘도록 설계

[한계 인지]

  • 헤딩·목차 구조가 없는 논문 같은 자유 서술형 문서는 참조할 경계 정보가 없어, 하이브리드 청킹이 사실상 고정 크기 청킹과 동일하게 동작

[2차 적용: LangChain SemanticChunker]

  • LangChain이 제공하는 SemanticChunker를 적용해, 인접 문장 간 임베딩 유사도가 급격히 떨어지는 지점을 의미 경계로 판단해 자동 분할하도록 설정
  • 구조 정보 없이 내용만으로 경계를 찾으므로 서술형 문서에 적용 가능

[성과]

3검색 정확도 고도화: Dense 단독 → (Dense + Sparse) BM25 하이브리드

[문제 상황]

  • 밀집(Dense) 임베딩 검색만 쓰면 의미가 유사한 문단은 잘 찾지만, 식별자·API 명세·고유명사처럼 정확한 문자열 일치가 필요한 검색에서는 실패
  • 파라미터명이나 에러 코드로 질문했을 때, 해당 문자열이 그대로 적힌 청크 대신 비슷한 주제의 다른 청크가 상위에 올라오는 현상 발생

[해결 과정]

  • 기존 Dense 검색만 쓰던 구조에 BM25를 추가해 하이브리드 검색으로 전환
  • RRF(Reciprocal Rank Fusion)로 Dense, BM25 각각의 검색 결과 순위를 합쳐 최종 순위 산출

[성과]

4RAG 성능 검증: 느낌 기반 판단 → RAGAS 정량 수치 평가

[문제 상황]

  • 청킹·검색 전략을 여러 차례 교체하면서도, 각 변경이 실제로 개선인지 답변 몇 개를 눈으로 보고 판단해온 상태 → 개선 여부와 회귀 여부를 객관적으로 확인할 방법 부재
  • 기능이 하나씩 늘어날수록 어떤 변경이 실제 성능 향상에 기여했는지 구분이 어려워지는 문제도 존재

[해결 과정]

  • RAGAS를 도입해 Faithfulness, Answer Relevancy, Context Precision, Context Recall 4개 지표로 파이프라인 품질을 정량 평가
  • 평가용 QA 테스트셋은 문서를 로컬 모델에 넘겨 자동 생성하고, 사람이 직접 검수·수정할 수 있도록 구성
  • 채점자도 LM Studio 로컬 모델을 그대로 사용

[성과]

  • 매 기능 변경마다 Before/After RAGAS 점수를 남겨, "느낌상 좋아졌다"가 아니라 변경 하나하나의 효과를 수치로 검증 가능한 구조 확보
  • 평가용 QA셋을 로컬 모델이 자동 생성하고 사람이 검수만 하는 구조라, 기능이 추가될 때마다 매번 QA를 새로 수작업하지 않고도 반복 평가 가능
  • 채점자 LLM도 로컬 모델을 사용해, 문서·평가 데이터가 외부로 나가지 않는 프로젝트 원칙을 평가 단계까지 유지

  • 파일 I/O 작업 시 스레드가 무한 대기 상태에 빠져 스레드 풀이 고갈되고, 서버 재기동이 강제되는 장애 전파 문제

[해결 과정]

  • 초기에는 Kubernetes Liveness Probe를 활용해 30초마다 마운트 상태를 검증하고 장애 시 파드를 자동 재시작하는 임시 복구 메커니즘을 검토했으나, 빈번한 서비스 중단 리스크를 인지하고 OS 의존성을 완전히 제거하는 SDK 직접 통합 방식을 최종 채택
  • 기존 파일 시스템 기반 I/O 코드를 AWS SDK를 활용한 API 통신 방식으로 전환하여 장애 격리 환경 구축
  • 네트워크 지연 및 장애 상황에 대응하기 위해 SDK 내 타임아웃 설정 및 예외 처리 로직 구현

[성과]

  • 운영 중 서버 재기동·파드 재시작 대응 건수를 하루에 7~8회에서 0회로 축소
  • 파일 시스템을 거치는 대신 AWS SDK로 S3와 직접 통신하게 하여, 불필요한 통역 과정을 없애고 데이터 접근 효율 개선

1멀티모달 LLM을 이용한 영상 청킹

[도입 배경]

  • 단순 시간 분할 방식은 문맥이 끊겨 자연스러운 숏폼 영상을 생성하기 어려움. 기존의 PDF/텍스트 청킹 방식과 달리, 영상 데이터는 시각적 흐름과 음성을 종합적으로 고려한 의미 단위의 분할이 필요
  • 분석된 타임라인과 장면 설명(Context) 데이터를 다음 파이프라인(RDBMS 저장 및 임베딩)으로 넘기기 위해, 응답 포맷의 규격화가 필수적

[해결 과정]

  • 의미 기반 청킹: Gemini(LLM) API를 활용하여 영상을 단순 프레임 단위가 아닌, 장면의 전환과 문맥의 흐름을 이해하고 의미 단위로 영상을 청킹(Chunking)하도록 프롬프트 엔지니어링 적용
  • JSON 응답 강제 (Structured Output): LLM 특성상 발생할 수 있는 비정형 텍스트 응답으로 인한 파싱 에러를 방지하기 위해, start_time, end_time, description 등의 필드를 명시한 JSON 스키마를 주입하여 지정된 JSON 형태로만 결과를 출력하도록 시스템 설계

[성과]

  • 영상의 문맥이 유지되는 청크 결과
  • LLM의 분석 결과를 정형화된 JSON 데이터로 변환하여, 파싱 예외 처리로 인한 서버 부하를 줄이고 RDBMS 저장 및 벡터 임베딩 과정으로의 데이터 연동 안정성 확보

2문장 기반 영상 검색 최적화 (벡터 검색 도입)

[도입 배경]

  • 기존 영상 검색 시스템은 키워드 기반 문자열 매칭 방식을 사용하여, 입력된 단어나 구문과 데이터 내 키워드가 정확히 일치해야만 검색이 가능해서, 표현 방식이 조금만 달라져도 관련 콘텐츠가 검색되지 않는 경우가 많았고, 대량 데이터가 쌓이면서 검색 속도 또한 점차 저하되는 문제가 발생

[사용 이유]

  • 검색 시스템의 정확도와 확장성을 개선하기 위해, 텍스트 데이터를 임베딩하여 의미 기반으로 검색할 수 있는 벡터 DB를 도입
  • 벡터 DB는 문장 간 의미 유사도를 수치화해 유사한 콘텐츠를 효율적으로 찾을 수 있으며, 대규모 데이터 환경에서도 빠른 검색을 제공
  • 이에 Gemini 임베딩 모델을 활용해 영상 데이터와 검색 입력 문장의 다양한 표현과 문맥을 인식하여 의미 기반의 벡터로 변환한 후 벡터DB에 저장 및 관리

[성과]

  • 문장 의미를 기반으로 유사 문장 검색 정확도가 크게 개선되고 데이터셋이 증가해도 성능 저하 없이 안정적으로 확장
  • 그러나 일반 DB에 저장된 영상 데이터를 벡터 DB에 임베딩하여 별도로 저장해야 하기 때문에, 동일 데이터를 두 시스템에서 관리하는 이중 관리 문제 발생. 이로 인해 데이터 동기화 작업 및 유지보수 비용이 추가로 발생하는 트레이드오프 발생

3영상 분리 작업 병렬 처리 Ray(라이브러리) 도입 후 한계

[도입 배경]

  • 쇼츠를 생성하려면 먼저 청킹 단계를 위해 원본 영상을 여러 조각으로 잘라야 하는데, 원본 용량이 클수록 이 작업이 오래 걸려 전체 생성 흐름이 지연되는 문제 발생
  • 영상 분리는 파일을 단순히 나누는 것이 아니라 조각마다 압축을 풀었다가(디코딩) 다시 압축(인코딩)하는 과정을 거치므로, 10분짜리 원본이면 60초 조각 10개를 각각 인코딩해야 해 영상이 길어질수록 시간이 비례해 증가
  • 영상 분리 작업은 I/O 바운드(영상 읽기 및 저장)와 CPU 바운드(비디오 디코딩 및 인코딩)가 혼합된 작업으로, Python의 GIL 제한을 고려해 멀티스레드 대신 멀티프로세스 기반 병렬 처리가 가능한 Ray를 도입하여 성능 최적화를 시도

[문제점]

  • 순차 처리 시 CPU 사용률은 30~50% 수준이었고, Ray 워커 5개로 병렬화하자 95~99%까지 상승
  • 그러나 처리 시간은 166초 → 144초로 약 13% 단축에 그쳐, 투입한 워커 수와 CPU 사용량에 비해 이득이 거의 없음
  • 실제 디코딩·인코딩은 Python이 아니라 moviepy가 띄운 별도 ffmpeg 프로세스에서 수행되므로, 도입 근거였던 GIL은 애초에 병목이 아님
  • 병렬화로 얻을 이득이 없다고 판단해 Ray 및 관련 의존성 제거

[추가 검증]

  • 최근 AI로 코드를 재분석해 "인코더 스레드 수를 제한하면 개선된다"는 답을 얻었으나, 그대로 적용하지 않고 Ray를 다시 도입해 스레드 수를 바꿔가며 직접 측정. 결과는 반대로 제한할수록 느려졌고, 인코더를 여러 개 동시에 돌리면 서로 간섭해 CPU만 더 쓰고 처리량은 늘지 않는 것이 실제 원인
  • 이후 접근을 바꿔, 영상 분리는 구간을 잘라내기만 하면 되는 작업이므로, 압축을 풀지 않고 그대로 잘라 복사하는 방식인 스트리밍 복사로 전환
  • 동일 조건에서 122초 → 2~3초로 단축되었고 재인코딩이 없어 화질 손실도 사라짐

4Celery를 활용한 비동기 태스크 큐 도입

[문제 상황]

  • 원본 영상의 용량이 클수록 영상 분리 작업 시간이 길어져, 사용자 경험(UX)이 저하되는 문제 발생
  • Flask와 Celery는 각각 독립적인 프로세스로 실행되므로, 큐에 담긴 작업이 실행될 때 Flask의 설정 및 데이터베이스 연결을 자동으로 사용할 수 없음
  • 특히, Flask에서 사용하는 ORM(SQLAlchemy)은 애플리케이션 컨텍스트 내에서만 정상적으로 동작하므로, Celery 태스크 실행 시 컨텍스트가 활성화되지 않으면 DB 관련 리소스를 참조할 수 없어 오류 발생

[해결 방법]

  • Celery 워커 실행 시 Flask 애플리케이션을 로드하여, Celery가 Flask의 환경 설정을 참조할 수 있도록 구성
  • Celery에서 큐에 담긴 작업을 실행할 때 자동으로 Flask 컨텍스트가 활성화되도록, Celery의 기본 태스크 동작 방식을 변경하여 커스텀 태스크 클래스를 적용
